## 摘要
Top-k稀疏注意力使长上下文LLM解码计算成本低廉：每一步仅读取选定的几千个KV条目，而非整个上下文。然而，服务系统通常将完整KV缓存保留在GPU HBM中，以确保每个位置始终可被选择，因此请求的内存账单仍随其完整上下文长度增长——解码在计算耗尽之前很早就遇到容量墙，且KV缓存超过HBM的上下文根本无法被服务。我们提出HiSparse，一种精确的、与索引器无关的分层KV缓存，用于稀疏注意力服务。HiSparse将每个请求的完整KV历史保存在主机内存中，并通过一个小的固定大小GPU缓存限制其解码占用；一个融合CUDA内核在解码CUDA图中解析每一层的选择——命中检测、LRU替换和主机到设备获取；对于跨层共享选择的模型，精确的逐层预取隐藏了约一半的剩余未命中开销。由于仅改变KV放置位置，模型输出不变。HiSparse已合并到上游SGLang，并在H200、B200和GH200平台上针对三个稀疏注意力家族（DSA、NSA和Quest）进行了评估：在长上下文工作负载上，峰值生成吞吐量提升高达4.7倍，同时保持可比的每token延迟，并在高负载下减少首token时间——一个无IO基准测试表明，解析机制本身不增加可测量的每token成本，仅剩主机-设备IO作为有界驻留的唯一代价。

## Abstract
Top-k sparse attention makes long-context LLM decoding cheap to compute: each step reads only a few thousand selected KV entries rather than the full context. Serving systems, however, typically keep the entire KV cache in GPU HBM so that every position stays selectable, so a request's memory bill still grows with its full context length--decoding hits a capacity wall long before it runs out of compute, and a context whose KV cache exceeds HBM cannot be served at all. We present HiSparse, an exact, indexer-agnostic hierarchical KV cache for sparse-attention serving. HiSparse keeps each request's full KV history in host memory and bounds its decode footprint with a small, fixed-size GPU cache; a fused CUDA kernel resolves each layer's selections--hit detection, LRU replacement, and host-to-device fetches--inside the decode CUDA graph; and, for models that share selections across layers, exact layer-wise prefetching hides roughly half of the remaining miss overhead. Because only KV placement changes, model outputs are unchanged. HiSparse is merged into upstream SGLang and evaluated across three sparse-attention families (DSA, NSA, and Quest) on H200, B200, and GH200 platforms: it improves peak generation throughput by up to 4.7x on long-context workloads while preserving comparable per-token latency and reducing time-to-first-token at high load--and a no-IO oracle shows the resolution mechanism itself adds no measurable per-token cost, leaving host-device IO as the only price of bounded residency.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：Top-k 稀疏注意力（如 DSA、NSA、Quest）将长上下文 LLM 解码的计算开销大幅降低——每个解码步骤只需读取选定的 k 个 KV 条目（通常几千个），而非整个上下文。但现有的服务系统仍将完整 KV 缓存驻留在 GPU HBM 中，以确保每个位置在未来的选择中始终可寻址。
- **核心矛盾**：稀疏注意力使每次解码的"活跃读取"缩减到 k，但 KV 缓存的"内存占用"仍与完整上下文长度成正比。这是一种失衡的服务经济学——注意力计算便宜了，内存账单却一个字节都没降。
- **容量墙的具体表现**：以 GLM-5.1 为例，128K token 的请求持有 13.09 GB BF16 KV 状态；1M token 的单个请求将占用超过 100 GB HBM（整个 H200 只有 141 GB，且需扣除权重占用），因此根本无法被接纳。实际中容量墙表现为"上下文长度 × 并发度"的乘积上限：在 32K 上下文时，几十个并发请求就耗尽 HBM；128K 时则只能容纳 4 分之一的请求数。
- **本文的核心洞见**：稀疏选择器本身就是一个"免费的预言机"——它在每一层解码前精确宣告将读取哪些 KV 位置。结合选择集在时间上（连续步骤间）和空间上（相邻层间）的强局部性，完全可以将 KV 缓存组织为"小快 GPU 缓存 + 大慢主机内存"的分层结构。
- **整体意义**：HiSparse 解耦了 KV 的"逻辑可用性"与"物理驻留性"，将容量瓶颈转化为可调的延迟/带宽问题，是首个将该方案真正落地到生产级服务框架（SGLang 上游）的系统。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 核心思想
- **分层 KV 层次结构**：主机内存（pinned DRAM）保存每个请求的权威完整 KV 历史；GPU HBM 仅为每请求每层保留固定大小（B 个槽位）的 GPU 缓存，B 是配置参数且 B ≥ k，与上下文长度 Lctx 无关。
- **关键不等式**：解码侧 KV 占用从 O(Nbatch·Nℓ·Lctx·WKV·s) 降为 O(Nbatch·Nℓ·B·WKV·s)，每请求在 GLM-5.1 上从 128K 上下文的 13.09 GB 降至 0.4 GB（~30 倍）。

### 三大技术挑战与解法

1. **驻留什么（缓存策略）**
   - 仅保留当前 top-k 集作为暂存区会丢失局部性（trace 显示 30% 未命中率），因此采用**每请求每层独立的 LRU 缓存**。
   - 细化策略：同一步内，命中条目在最近性顺序上排在新增的未命中条目之上，使有多次复用记录的位置在驱逐压力下留存。
   - 在 LongBenchV2 选择 trace 上，B=2k 时 LRU 达到 87% 命中率；B=4k 时进一步升至 93.3%。

2. **隐藏剩余未命中（IO 优化与预取）**
   - **GPU-assisted IO**：借鉴 Strata，GPU 线程直接以向量化非一致性加载（`ld.global.nc.v2.b64`）从 pinned 主机内存读取散乱地址，按调优块大小接近链路带宽。
   - **精确逐层预取**：针对跨层共享索引的模型（GLM-5.2 的 IndexShare、IndexCache），anchor 层发出选择集后，后续共享层的选择即已知。anchor 的 RESOLVE 内核记录"未命中计划"，侧流上的纯拷贝内核将该计划重放到各共享层缓存中，与中间层的计算重叠。共享层复用 anchor 的槽表，直接等待预取完成事件，完全跳过解析。
   - 反例：对无共享索引的模型尝试的**投机性预取**（用层 ℓ 的选择预测层 ℓ+1）几乎无端到端收益，因为 LRU 已捕获大部分隐式跨层复用，而真正的未命中恰是预测不到的。

3. **让解析本身廉价（融合 CUDA 内核 RESOLVE）**
   - 单次内核启动完成全部解析工作，捕获在 SGLang 解码 CUDA 图中，无主机侧分支。
   - **五阶段流程**：(1) 将选中位置构建为共享内存哈希表；(2) 并行探测 GPU 缓存每个槽位，标记命中/可驱逐；(3) 并行扫描选择受害者并更新 LRU 元数据；(4) 批量向量化加载缺失 KV 记录；(5) 发布 `top_k_device_locs` 物理槽位向量给稀疏注意力后端。

### 请求生命周期
- **四个阶段**：预填充与暂存（KV 写入主机池）→ 准入（按 B 而非 Lctx 预留 HBM）→ 逐层解码（RESOLVE + 稀疏注意力）→ 新生成 KV 写穿（直接写入 GPU 缓存保留槽，后台流回写主机池）。
- **索引器状态永不移动**：DSA 的索引键、NSA 的压缩块键、Quest 的页摘要等紧凑选择状态始终驻留 GPU，每 token 仅几百字节，远小于 KV 记录的 ~100 KB/token。

## 6. 论文的主要结论与发现

- **吞吐量大幅提升**：峰值生成吞吐最高提升 4.7×（Qwen+Quest 在 200K 上下文，111→520 tokens/s）；各模型在 32K 处提升 2.1~3.6×。
- **延迟代价可控**：在重叠的吞吐量区间内 TPOT 与基线相当（16.0 vs 15.9 ms，DSv4-Flash 并发 16）；HiSparse 的本质收益来自更大的解码批次而非更快的单步。
- **TTFT 在高负载下显著降低**：如 DSv4-Flash 并发 64 时，基线 TTFT 829s，HiSparse 仅 171s。
- **LRU 是有效的在线替换策略**：miss rate（B=2k）为 13.4%，优于 FIFO（17.2%）和随机（16.1%），趋势接近 Bélády 最优（8.2%）；B=4k 时 LRU 降至 6.7%。
- **解析机制本身零开销**：无 IO oracle 在低并发时 TPOT 与基线持平（24.1 vs 24.8 ms），证明 HiSparse 的全部每 token 开销都是主机-设备 IO。
- **精确预取隐藏约一半剩余 IO 开销**：GLM-5.2 上精确预取使 TPOT 降低 13-15%、吞吐提升 14-17%，从无预取时的 1515 提升至 1727 tokens/s，达到无 IO 预言机上界（2034）的 85%。
- **硬件趋势偏好**：更快的主机-设备链路（NVLink-C2C vs PCIe Gen5）使 IO 代价大幅压缩（GLM-5.1 从 112 到 29 μs/调用），将最优缓存比移向 B=2k。

## 7. 优点：方法与实验设计亮点

1. **索引器无关的简洁接口**：HiSparse 只消费各层发出的逻辑 token 位置，插在"选择"与"读取"之间的自然间隙，对 DSA、NSA、Quest 全部适用，无需重训或改模型。
2. **精确性承诺**：仅改变 KV 放置位置，不改变选中集、注意力分数或输出——不存在检索式方法的近似偏差问题。
3. **设计闭环完整**：从容量墙问题的量化识别，到 LRU 策略的 trace 验证，再到 RESOLVE 融合内核和预取的细致消融，每一环节都有对应实验支撑。
4. **生产级落地**：约 2,200 行 Python + CUDA 内核头文件，合并进 SGLang 上游作为正式特性，包含与 HiCache（前缀缓存）的组合定位，工程上具有很强的可复现性。
5. **显式上界方法**：无 IO 预言机（虽然输出无效，但作为时序上界）清晰地界定了任何 IO 隐藏方案的理论天花板，使性能分析不流于表面。
6. **诚实的负结果报告**：投机预取无收益的结论被如实呈现，并导向"模型协同设计（共享索引）"的正确方向，避免了为方法论凑证据的倾向。

## 8. 不足与局限

1. **TPOT 开销无法完全消除**：同步解析时低并发匹配下每 token 暴露 7-8 ms IO 开销；精确预取后仍约 3 ms。在短上下文（4K 以下）或非容量受限场景下 HiSparse 无收益，需在部署时按场景开关。
2. **主机内存容量是新瓶颈**：HiSparse 的前提是"第二层远大于第一层"，PCIe H200 服务器的 TB 级主机 DRAM 成立，但在 Grace 架构（GB200/GB300）上，Grace CPU 的 ~480 GB LPDDR 与 GPU 聚合 HBM 相当甚至更小，容量倍增效应大打折扣。NVMe/网络扩展可行但延迟更高。
3. **物理上未验证 PD 分离部署**：端到端实验均为 PD 共置模式，分离模式用"仅解码"曲线作代理，未在真实分离集群上测量预填充-解码传输对主机池的额外压力。
4. **实验覆盖的边界**：并发扫描集中在 32K 上下文；更长上下文的曲线不完整，因为基线在低并发即骤降。服务器级缓存配置（B 的选择）依赖人工 profile 扫描，尚无动态调节策略。
5. **与同期工作的对比缺失**：ESS 和 ECHO 因属同期工作而未被直接对比，读者难以定位 HiSparse 相对最接近竞品的精确优势幅度。
6. **跨层共享索引依赖模型协同设计**：精确预取在 GLM-5.2（自带 IndexShare）上才有效；对无共享索引的模型，投机性替代方案被证明几乎无效，方案的普适性受限于模型架构新趋势。
